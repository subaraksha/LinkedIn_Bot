# Portable owner knowledge — Phase 2 contract

**Status:** Approved design for PRD and architecture revision 1.4; format and schema will be implemented in Phase 2. This file contains no owner profile data.

## Purpose and authority

The owner can reuse their professional knowledge in a portfolio or another application without access to this application's MongoDB database or model session. MongoDB is the working source of truth. Exported files are portable snapshots of the last committed profile revision. An external program may read them; editing a file does not silently edit the active profile.

Only information persisted as owner profile data belongs in the export. Gemini proposals are labelled as pending until reviewed. Unstored model context is not treated as a hidden knowledge store. Raw Telegram history, drafts, LinkedIn tokens, bot credentials, session cookies, pairing challenges, and publication approvals are outside this profile format.

## Owner-facing files

The dashboard offers two separate actions:

1. **Download full knowledge:** a private bundle with structured `profile.json`, readable `profile.md`, `manifest.json`, and the published JSON Schema. It contains current confirmed, pending, and disputed facts with status and permission labels; sources and bounded evidence; answers and skipped questions; goals, preferences, and optional writing samples. The owner may explicitly include original uploaded files in a `sources/` directory. Originals are absent by default.
2. **Download public profile:** a separate bundle generated by an allowlist from the same committed revision. It contains only confirmed facts explicitly permitted for public use and safe display preferences. It does not contain private, pending, disputed, or deleted claims; private evidence excerpts; original files; confidential exclusion lists; or unapproved clarification answers. A public fact may include a source link only when that source itself is public and approved for display.

Files are written under ignored `APP_DATA_DIR/exports`, with owner-only local permissions. The dashboard serves a download as an attachment after session checks. Full and public bundles have visibly different names and privacy labels. Nothing is automatically committed to Git or uploaded to another service.

## Structured contract

The implementation publishes `profile.schema.json` with an explicit JSON Schema dialect and `format_version`. A portable reader needs only the JSON files and schema. Markdown is a human-readable rendering of the same current data and is not the import format.

`manifest.json` includes `format_version`, `scope` (`full` or `public`), `profile_revision`, `generated_at` in UTC, the JSON Schema identifier, and a SHA-256 hash and byte length for each included file. Optional originals use generated relative filenames and source IDs; neither a source title nor an uploaded filename becomes a filesystem path. All bundle paths are relative and contained within the bundle.

`profile.json` uses stable IDs rather than prose matching. Its full scope includes:

| Field group | Required meaning |
| --- | --- |
| `profile_revision` and timestamps | Identify the exact committed owner profile snapshot. |
| `facts` | ID, type, claim, status, publication permission, experience context, revision, update time, and evidence references. |
| `sources` | ID, kind, display metadata, content hash, parser/source version, and bounded excerpts or references needed to understand fact provenance. |
| `clarifications` | Question ID, status (`pending`, `answered`, or `skipped`), answer when provided, and linked fact/source IDs. |
| `goals` and `preferences` | Target roles/audience, interests, writing choices, optional samples, and confidential boundaries. |
| `suppression_markers` | Minimal non-claim identifiers/hashes needed to stop deleted facts from being re-extracted as active claims. |

The public scope uses its own documented schema/projection and omits fields by allowlist. An importer must never infer that a missing private field is public. Every retained evidence reference must resolve to an included source or an explicitly documented external public URL. Timestamps are UTC ISO-8601 strings; IDs and enum values are stable across exports of the same profile revision. Schema changes increment `format_version` and ship a migration or a clear unsupported-version error.

## Freshness and failure behavior

Each accepted source, fact, clarification, or preference change increments `profile_revision` in the same MongoDB transaction as that change. Export generation reads one consistent committed snapshot. After a successful database commit, the application writes the full local snapshot to temporary files, validates schema and file hashes, fsyncs, then atomically replaces the previous export. `export_revision` advances only after this succeeds.

If writing fails, the database edit remains saved. The dashboard shows the last export revision as **outdated** with a Retry action. It never labels the previous file current or silently serves it as the latest download. A requested download creates a fresh export or reports the failure. A public bundle is produced only on request from a current validated snapshot; it does not inherit private data from a previously generated bundle.

## Import and independent reuse

The full JSON bundle is the re-import contract. Import first validates format version, schema, file hashes, relative paths, size limits, source/evidence references, enum values, and privacy labels. Preview shows what would be added or conflict with the active profile and performs no write. Apply requires the local owner session and expected profile revision. By default, import targets an empty profile; merging into a populated profile requires explicit per-conflict decisions. Import never restores credentials, bot/account connections, jobs, workflows, drafts, approval receipts, or permission to publish.

A portfolio or other application can read `profile.json` independently and choose its own presentation. The public bundle is the safer starting point for a public portfolio. There is no automatic two-way sync; a changed external file returns through the validated import path.

## Phase 2 acceptance checks

- A confirmed correction appears with its latest revision and evidence in both full JSON and Markdown. A pending inference remains labelled pending; an unresolved conflict remains disputed.
- A private canary fact, private source excerpt, confidential exclusion phrase, and optional writing sample are absent from every public bundle. Only confirmed and explicitly public facts appear there.
- A deleted claim is absent from active exports and does not reappear when the full bundle is imported into a uniquely named temporary database.
- A separate reader validates the JSON against the published schema and follows each source/evidence ID without application code or database access.
- A full bundle round-trips through a temporary database, preserving IDs, statuses, fact permissions, provenance, goals, and preferences. Import creates no publication approval.
- Corrupted hashes, unsupported versions, unsafe paths, invalid permissions, and references to missing sources are rejected before any import write.
- An export write failure after a committed profile edit leaves the edit saved, keeps the prior bundle intact, shows an outdated revision, and succeeds on retry.
- The full bundle contains no provider credentials, session secrets, approval challenges, or unrelated raw conversation history; both export directories and generated bundles are ignored by Git.
